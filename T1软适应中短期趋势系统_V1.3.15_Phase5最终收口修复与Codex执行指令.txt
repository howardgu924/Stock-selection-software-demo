2. P0-1 核心策略链不得由调用方替换

现有问题：
RunOrchestrator只检查依赖是否callable，调用方可传返回空字典的lambda替代真实Phase 1—4B逻辑，事件仍COMPLETED。

必须修复：

2.1 删除可替换的核心函数依赖

以下行为不得作为可注入callable：
- Phase 1 OpportunityScore；
- Phase 2 MarketOverlay、Divergence、RiskOverlay、ExecutionGate；
- T1Risk；
- Phase 4A PositionSizing、PortfolioAllocator；
- Phase 4B硬退出、coordinate_1430_exit_cycle、PendingSell转换、TrailingStop更新；
- Phase 3 FillEngine；
- Phase 4A apply_buy_fill/apply_sell_fill。

RunOrchestrator必须在模块内部直接导入并调用权威函数。不得再通过dependencies.phase1、dependencies.coordinate_1430、dependencies.valuation等入口替换核心实现。

2.2 允许注入的依赖

依赖对象只能提供数据或外部适配：
- MarketView或原始行情读取；
- TradingRuleSnapshot、FeeRuleSnapshot；
- AccountSnapshot、UniverseSnapshot、DataSnapshot；
- Provider适配；
- 时钟；
- 测试故障注入；
- 可观察性回调。

这些依赖不得返回最终策略决策。

2.3 RuntimeHooks

RuntimeHooks只能用于before/after观察、指标、日志和测试异常注入。默认空RuntimeHooks合法，但不能跳过核心链。

核心权威函数、数据读取器或规则快照缺失：
- run失败；
- 错误码INVALID_CONFIG或UNEXPECTED_ENGINE_ERROR；
- 事件不得COMPLETED。

2.4 固定流程

2. 真实MarketOverlay和EntryThreshold；

BAR_CLOSE内部直接调用真实Phase 4B硬退出。

DECISION_1430内部直接调用真实coordinate_1430_exit_cycle，不得存在替代入口。

3. P0-2 日终mark必须由编排器选择和验证

现有问题：
dependencies.valuation可直接返回任意close=999，编排器只校验有限正数。

3.1 删除最终mark注入

依赖不得直接提供：
- position_marks；
- final_close；
- final_equity；
- unrealized_pnl；
- 已选择估值价格。

依赖只能提供原始候选：
- 当日5分钟K线；
- 交易状态；
- 上一交易日mark；
- price_basis_id；
- TradingRuleSnapshot；
- ATR20和日线数据。

3.2 权威选择函数

实现不可替换的select_session_close_mark：

输入至少有symbol、trade_date、当日5分钟bars、previous_valid_mark、trading_rule_snapshot、expected_price_basis_id。

固定顺序：
1. 14:55 bar完整合法且price_basis一致，使用14:55 Close；
2. 否则按bar_start降序选择当日最后有效Close；
3. 当日明确全天停牌，使用previous_valid_mark；
4. 否则MISSING_MARK_PRICE并DEGRADED。

不得使用未来交易日数据。

3.3 有效性

mark必须：
- Decimal或精确十进制；
- 有限且>0；
- bar.trade_date等于当前日；
- 合法5分钟bar_start；
- OHLC合法；
- price_basis一致；
- source属于data_snapshot；
- bar已完成。

previous_valid_mark只在当日明确全天停牌、来自更早交易日且price_basis一致时允许。

3.4 Equity

HoldingValue=total_qty×selected_mark
Equity=cash+ΣHoldingValue

依赖不得覆盖。

3.5 TrailingStop

使用同一个权威mark和ATR20调用真实Phase 4B更新函数。无有效mark时保持旧状态并记录MISSING_MARK_PRICE。

3.6 测试

2. 14:55有效选14:55；
3. 14:55无效但14:50有效选14:50；
4. bars乱序仍选最后合法时间；

6. 非停牌无当日mark时DEGRADED；
7. 昨日mark price_basis不一致时拒绝；
8. bar日期不是当前日时拒绝；
9. 开放持仓Equity正确；
10. TrailingStop只用权威mark且次日生效。

4. P0-3 恢复Cooldown必须按checkpoint时点

现有问题：
恢复时使用整个回测最后交易日作为as_of，导致尚未到期的Cooldown被提前过滤。

4.1 恢复时点

resume_run计算recovery_as_of_trade_date，来源：
1. 最后COMPLETED checkpoint事件的trade_date；
2. 无checkpoint时使用run首个交易日前一实际交易日或明确初始状态日期；
3. 判断下一事件可交易性时使用next_pending_event.trade_date。

不得使用date_range.end_date、当前自然日或最终交易日。

4.2 Cooldown加载

恢复时保留所有：
reentry_allowed_date > recovery_as_of_trade_date

下一事件日期D：
D < reentry_allowed_date时blocked；
D == reentry_allowed_date时允许。

4.3 Checkpoint

checkpoint明确保存：
- event_id；
- trade_date；
- event_time；
- sequence_number；
- next_event_id或足以确定下一事件的信息。

4.4 测试

1. 回测1月2日至10日；
2. 1月3日中断；
3. Cooldown至1月6日允许；
4. 恢复后1月4、5仍blocked；
5. 1月6允许；
6. 最终交易日不影响恢复；
7. 周末和休市日正确跳过；
8. 无checkpoint初始恢复；
9. 多次resume一致；
10. checkpoint与下一事件边界。

5. P1-1 缓存与Ledger审计必须完整

5.1 缓存审计

缓存发生在run创建前时，可使用market_cache_audit表，或adaptive_v13_audit_events中的preparation_id/data_snapshot_id。

至少记录：
CACHE_LOOKUP、CACHE_HIT、CACHE_MISS、CACHE_PARTIAL、MISSING_TRADING_DATES、PROVIDER_ATTEMPT、PROVIDER_REJECTED、PROVIDER_FALLBACK、PARTITION_VALIDATED、PARTITION_INVALID、DATA_READINESS_READY、DATA_READINESS_FAILED、DATA_SNAPSHOT_CREATED。

字段至少包含：
preparation_id或run_id、data_snapshot_id、logical_key、symbol、dataset_type、source、source_version、action、status、reason_code、covered_dates_hash、missing_dates_hash、input_hash、output_hash、created_at。

Provider回退必须记录首个Provider被拒原因和最终来源。

5.2 Ledger审计

每个LedgerEvent在同一事件事务内写独立AuditEvent：
- component=account_ledger；
- action=BUY_CASH_DEBIT或SELL_CASH_CREDIT；
- fill_id；
- ledger_event_id；
- cash_before；
- cash_delta；
- cash_after；
- fee_total；
- status；
- reason_code。

不得用fill_engine审计替代Ledger审计。

同一ledger_event_id重放：
- 不重复记账；
- 不重复写第二个成功审计。

5.3 报告审计

报告审计日志必须包含cache、DataReadiness、Fill、Ledger、Pending、ExitControl、Cooldown、Recovery和Report。

缓存审计若不属于具体run，manifest引用preparation_id或data_snapshot_id，并纳入相关缓存审计。
